### External reference code convention

Every code we own is **SCREAMING-KEBAB, hyphenated at every word boundary**. Chosen
because it was already dominant and hand-authored that way: `ELEARNING-SPACE`,
`SITE-MYMASTERCLASS`, `CMS-DOC-COURSE-1-IMAGE`.

```
ELEARNING-COURSE-SHORT-DESCRIPTION      object field
MY-COURSE-ENROLLMENT-CONFIRMING-ENROLLMENT   object action
CMS-FIELD-TITLE-ELEARNING-BLOG          hand-authored field code
```

**Two namespaces are deliberately left alone.**

- `L_CMS_CONTENT_STRUCTURES`, `L_FILES`, `L_USER` reference entities **Liferay ships**.
  They are referenced here and defined elsewhere, so renaming one breaks the link to
  Liferay's own object folder or user object.
- 12 UUID codes sit on Liferay's **system fields** (`creator`, `createDate`, `id`,
  `modifiedDate`, `status`). They arrive in an instance export and are what an import
  matches on.

**The legacy batch keeps its own style on purpose.** `liferay-masterclassobj-batch` uses a
solid entity name with hyphenated suffixes — `MYCOURSE`, `MYTEACHER-PHOTO`,
`MYCOURSE-BATCH-1` — against the shipping batch's fully hyphenated `MY-COURSE-ENROLLMENT`.

That difference is a safety feature, not an oversight. The two batches should never deploy
to the same instance, but nothing prevents it. Keeping the styles distinct means an
accidental joint deploy produces two separate objects rather than silently colliding on a
shared code. Verified: zero codes are shared between them. The legacy tree also has to keep
provisioning unchanged, because it is the "before" state the migration is shown against.

**Changing a code changes an object's identity.** On a clean database that is invisible.
Against an instance where the objects already exist, the next import creates *new*
definitions alongside the old rather than updating them. Reprovision from clean, or restore
a snapshot, after any change here.

**Verify by reading the list, not by asserting a property.** Two bugs got through automated
checks during this work: `courseID` became `COURSE-I-D` (the camel split fired before every
capital), and `MYENROLLMENTSTATUS` became `M-Y-E-N-R-O-L-L-M-E-N-T-S-T-A-T-U-S` (an all-caps
name has a boundary before every letter). The check at the time looked for codes with *no*
hyphen, so an eighteen-hyphen code passed. Both were caught by a human reading the output.
There are only ~168 codes — print them all and look.

### An object relationship cannot cross a Space boundary

Verified in `ObjectRelationshipLocalServiceImpl` on current master (and unchanged from a
year ago):

```java
if ((objectDefinition1.getScope() == SCOPE_DEPOT ||
     objectDefinition2.getScope() == SCOPE_DEPOT) &&
    objectDefinition1.getScope() != objectDefinition2.getScope()) {
    throw new ObjectDefinitionScopeException(...)
}
```

A Space is a depot/asset library, so `SCOPE_DEPOT` is what an object in one carries. Both
ends of a relationship must share a scope. This settles two questions that were open:

| Object | Scope | Why |
| --- | --- | --- |
| `ElearningCourse`, `ElearningSession` | `depot` | Content, in the Space, gets the new CMS |
| `MyCourseSession`, `MyCourseEnrollment` | `company` | Operational, outside, so they can relate to each other |

**`courseID` is a `LongInteger` by necessity, not by oversight.** Enrollment is company
scoped and the course is in the Space, so a real relationship between them throws at
provision time. A loose ID is the only option. Do not "fix" it.

**`MyCourseSession` is not a redundant duplicate of `ElearningSession`.** It is the company
scoped counterpart that exists so `enrollmentToCourseSession` has two same-scope ends.
Deleting it and pointing enrollment at `ElearningSession` would throw. It is load bearing.

The trade-off is worth stating plainly, because it is not obvious until something throws:
putting content in a Space buys the new CMS and costs referential integrity with anything
outside it. Nothing prevents an enrollment holding a `courseID` for a course that no longer
exists.

### How to split the work

### Verify as the visitor, always

Every failure mode in this stack is silent. An unauthenticated `curl` is a Guest request and
is the only cheap way to see what a visitor sees. An object backed collection renders **empty**
for Guest until `resource-permissions.json` grants `VIEW` at company scope `"1"` — and a page
that looks blank is more often a missing grant than a bad mapping.

### A depot scoped object's entries are NOT at `/o/c/<plural>`

This cost most of the session and will cost the next person the same, because the error
message points somewhere else entirely:

```text
GET /o/c/elearningcourses  ->  409  "Conflict with getObjectEntriesPage"
```

That reads as a duplicate REST path. It is not — there were no duplicate paths. The
correct call is the **scoped** variant, keyed on the Space's `siteId`:

```bash
curl --silent --user 'test@liferay.com:test' \
	--url "http://localhost:${PORT}/o/c/elearningcourses/scopes/36372?pageSize=100"
```

Two identifiers are easy to transpose and both return plausible failures. From
`GET /o/headless-asset-library/v1.0/asset-libraries`:

| Field | Value here | Use |
| --- | --- | --- |
| `id` | `36371` | The depot entry ID. As a `scopeKey` it returns `404 NOT_FOUND`. |
| `siteId` | `36372` | **The groupId. This is the `scopeKey`.** |

A wrong `scopeKey` gives `404`, which reads as "the endpoint does not exist" rather than
"wrong scope" — so it sends you back to doubting the path you had just got right.

**Why**, verified at source — `ObjectDefinitionDeployerImpl._processMethods`:

```java
boolean groupAware = objectScopeProvider.isGroupAware();
boolean hasScope = value.contains("scopes");

if ((!groupAware && hasScope) ||
	(groupAware && !hasScope && !value.startsWith("/{objectEntryId}"))) {

	excludedOperationIds.add(method.getName());
}
```

A group aware scope provider — site or depot — excludes **every** unscoped collection
operation and keeps only the `/scopes/{scopeKey}` forms. The deployer writes those names
into a `VulcanCompanyConfiguration` keyed on the object's REST context path, and
`ContextContainerRequestFilter._filterExcludedOperationIds` aborts the request with
`409 Conflict with <methodName>`. So the 409 is a deliberate exclusion, not a collision.

Company scoped objects are unaffected: `/o/c/mycoursesessions` answers normally.

### Two wrong turns worth not repeating

- **It is not about the CMS object folder.** Liferay's own `CMSBasicWebContent` and
  `CMSBlog` 409 identically, which looked like proof that content structure objects close
  their entry API by design. They do not — those objects are depot scoped too, and the same
  `scopes/{scopeKey}` path serves them. There is no separate CMS REST module; `/o/cms/...`
  is just a `restContextPath` set on the system objects.
- **It is not the root descendant branch.** The sibling exclusion in `_excludeMethods`
  (`!isAllowStandaloneObjectEntry() && isRootDescendantNode()`) drops the same 16 operation
  IDs, so it is an easy misattribution. It does not apply here: that tree is built from
  relationships flagged `edge: true`, and all three `ElearningCourse` relationships are
  `edge: false`.

### Relationship ERCs were UUIDs — fixed 5 Oct

The ERC standardisation covered definitions, fields and picklists but not object
relationships, so all five were generated UUIDs that differ on every bundle. Moving them
into the tree closed it: they now read `ELEARNING-COURSE-TEACHERS`, `-MODULES`,
`-SESSIONS`, `MY-ENROLLMENT-TO-COURSE-SESSION` and `MY-COURSE-TO-USER`.

**This was never cosmetic.** `_addOrUpdateObjectRelationships` upserts by
`(externalReferenceCode, objectDefinitionId1)`. A batch created relationship with a
generated UUID makes that lookup miss, so the tree posts a second one and the add throws
`DuplicateObjectRelationshipException` — **inside site creation**, so every later provision
rolls the whole site back. Deleting the site does not clear it, because relationships are
company scoped; recovery is deleting the UUID relationship by hand.

It bit twice during the work, both times from batch units replaying after a restart even
though the deployed zip no longer contained them. Expect it on any instance that ran the
old batch.

## The measurement work

Regression tests for the MD files in `.agents/`, run with `claude plugin eval`.

The subject is instructions for a non deterministic agent, so a single passing run
proves nothing. The suite answers two separate questions:

1. Does the skill reach the right conclusion **reliably** — hence `--runs`.
2. Did the skill **cause** it, or would the model have got there alone — hence the
   ablation arm.

A case scoring 1.00 with a delta of 0.00 means the model already knew. That content is
documentation, not instruction, and should be cut or sharpened.

## Running

```bash
# The whole suite: 5 runs per case, with a no-plugin baseline arm

claude plugin eval . --eval-dir evals --runs 5 -j 4 \
	--trust-plugin --no-publish --scaffold --judge-model sonnet \
	--json /tmp/eval.json

# One case while iterating

claude plugin eval . --eval-dir evals --case fact-batch-directory --runs 5 \
	--trust-plugin --no-publish --scaffold --judge-model sonnet
```

Every flag there is load bearing:

| Flag | Why |
| --- | --- |
| `--scaffold` | Without it `scaffold_script` does not run and every case executes against an **empty workspace**. The run still scores — as zero. |
| `--judge-model sonnet` | The default judge is haiku, and llm graders are noisy on long inputs. A compound rubric judged by haiku false-failed 9 runs out of 10 here. |
| `--trust-plugin` | Skips the first-run trust prompt. |
| `--no-publish` | Keeps the HTML report local. |

Results land in `evals/results/` (gitignored).

The filter is sharper than "facts vs reasoning", which was the first guess and is wrong.
Everything that measured zero — `ResourceConstants` scope values, dangling
`ObjectDefinition#XXXX`, `[#…#]` delimiters, resolving numbered fieldsets into a related
object — is **documented API surface or ordinary modelling**, and the model has it.

The one case that measures large is **undocumented implementation behaviour**: you cannot
derive that `BundleSiteInitializer` silently skips `batch/` from any published document,
only from reading the source or losing a day to it.

So the test for skill content is **"could someone find this in the documentation?"** If
yes, the model already knows it. Write new cases against behaviour that is only
discoverable from source or from failure.

## Conventions

- **Prompts are phrased as a user would phrase them**, never "use the
  migrate-cms-to-objects skill". Whether the skill fires on its own is part of the test.
- **Invite the wrong answer** where the fact is counterintuitive. `fact-batch-directory`
  asks "I was going to drop it in `site-initializer/batch/` — is that right?" Baseline
  says yes, five times out of five, in seven turns.
- **Prefer `regex` graders.** The type hierarchy is verifiable → binary → n-ary → llm
  rubric. Use `llm` only for what regex cannot capture, and write the rubric as one
  checkable claim.
- **Never one grader at weight 1.** A single compound rubric is a single point of
  failure; one misfiring clause zeroes the case. Several narrow weighted graders turn a
  misfire into a partial score, which is also diagnostic.
- **Assert what must be identified, not how it must be explained.** A rubric that encodes
  the author's causal story measures agreement with the author. `fact-permission-scope`
  failed a response that named the right cause, gave the right constants and the right
  fix, because it explained the mechanism differently from the rubric. Three separate
  designs of that one case produced three false results before the grader was fair.
- **Avoid `not_contains` on a term a good answer would mention.** A response saying
  "do not use X" fails a negative regex on X. This retired a grader here.
- **Ship the reasoning, not just the rule.** `fact-permission-scope` measured delta 0.00
  while the skill assisted run stated the wrong `ResourceConstants` mapping and baseline
  got it right. The skill carried the bare prohibition "never scope 3" with the constants
  table in an unshipped card. Given a rule and no reasoning, the model invents the
  reasoning, and a confident wrong explanation reads exactly like a correct one.
- **Grant the tool a discipline check needs.** Asserting "it did not write" proves
  nothing when `Write` was withheld — grant it with `--allow-tools Write Edit` so
  restraint is a choice.

## Harness gotchas

- **There is no dry run.** `claude plugin eval` with no `--case` filter runs the whole
  suite. To check cases merely load, use `--case __none__`.
- **`scaffold_script` goes under `context:`**, not `execution:`. Misplaced, it is
  silently ignored and the workspace stays empty.
- **`add_dirs` cannot escape the case directory** — no `..`, no absolute paths. Fixtures
  must live inside the case, which is why they are committed copies rather than pointers
  at `client-extensions/`.
- **The workspace must resolve as a plugin**, or the harness silently falls back to
  baseline and reports `plugins: []` — cases still run and still score, so a suite can
  look like it is exercising a skill while measuring the model alone. That needs
  `.claude-plugin/plugin.json` at the repo root with components at `<root>/skills`.
- `case.yaml` needs `schema_version`, `name`, and the prompt under `execution.prompt`.
- **A usage limit scores zero, it does not fail the run.** A limit truncated run comes
  back as a clean `0.00` in both arms with delta `0.00`, which is indistinguishable from
  a real "no uplift" result. Only the per run `error` field says otherwise. Check it
  before believing a zero.
- **`evals/` vanishing from the working copy** means a branch tracked it. A `.gitignore`
  entry only protects the branches that carry it, so a rule added on a feature branch
  does nothing for a branch cut from `master` — `git add -A` there will sweep the suite
  into a PR, and checking back out deletes it. The rule now lives on every branch that
  can see `evals/`; it belongs on `master` at the first opportunity.

## Fixtures

Each case owns a frozen copy of the files it needs, under `<case>/fixture/`. They
duplicate content from `client-extensions/`, deliberately: a case pointed at the live
tree would silently go green the moment someone fixed the defect it tests.

`evals/` is gitignored — the suite carries ~450KB of fixture and does not belong in a
PR. Commit deliberately with `git add -f` if that ever changes.
